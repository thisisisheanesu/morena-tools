# 46 — Fine-tuning nano and mini for Nigerian fintech tool calling

Follows docs/44, which measured the released lineage against a menu built from the real Paystack
OpenAPI spec, and docs/45, which specifies the demo this is meant to make recordable.

## What docs/44 found, and why the data was the cause

Three failures, all measured, all traceable to one line of the corpus builder.

**9% correct tool selection** on the Paystack menu, against 97% on the menu the model was trained
with. `build_sft_v17.py` does not use each example's own menu. It calls `scan_tools()` to collect
every tool in the corpus into one global pool, then `tool_menu()` builds each prompt from the
correct tool plus three distractors drawn from that pool. Roughly fifteen names, shared across every
tool-calling example in the SFT set. The model had no reason to read the schema in front of it,
because the answer was always recoverable from the name alone. Adding `aliases` to the Paystack menu
lifted it from 9% to 77%, which is the signature of name recall rather than schema reading.

**Edits corrupt untouched fields, 6 runs out of 6.** Given a pending call and asked to change one
field, the model re-emitted the entire call and changed an amount nobody had touched. There is no
patch-shaped example anywhere in the corpus; every tool example is a single turn that emits a whole
call, so a whole call is the only thing it knows how to emit.

**It calls tools when it should not.** Same cause from the other side: no example shows a menu and
then answers in prose.

## The data

20,000 jobs, **20,000 distinct menus**, one per record, generated by `seed_tools_v2.py` across five
naming conventions (`paystack`, `verbnoun`, `camel`, `dotted`, `terse`) with an argument-synonym
table, so nothing but the format is shared between two examples. Nigerian languages are
double-weighted. Four types:

| type | teaches | dup |
|---|---|---|
| `toolcall_api` | read an unfamiliar schema, call, answer from the result | 1 |
| `toolpatch` | emit **only** the changed fields | 3 |
| `toolrefuse` | answer in prose, call nothing (incl. benign-answered) | 2 |
| `tooldisambig` | ask one clarifying question, *then* call | 3 |

Patch and disambiguation are upsampled because they are behaviours the released model does not have
at all, rather than behaviours it has badly.

### Yield

93.2% survive `validate_tools_v2.py` on a 2,224-record sample, matching the 93.3% pilot. The rejects
are worth naming: `toolpatch:bad_op` 131, `toolrefuse:emitted_a_call` 20, `no_answer` 1.

Almost all of the `bad_op` rejects are **empty completions**, not wrong ones: `finish_reason=length`,
`retried=true`, `output=""`. `toolpatch` has the longest prompt of the four (menu plus the pending
call) on the second-smallest token budget, and burned it on reasoning. Budget raised 2500 → 3500 for
`toolpatch` and 3000 → 3800 for `tooldisambig`, which fails the same way at 21%. Not redeployed
mid-run: ~1,100 jobs remained and a deploy that goes wrong costs more than the ~190 records it saves.

The check that matters passed. **0 of 427 patches restate a field the user did not mention.** That is
the 6-out-of-6 corruption bug, absent from the training data by construction.

## Format

`build_tools_v18.py` is separate from `build_sft_v17.py` precisely so that `scan_tools`/`tool_menu`
cannot touch it. Each record's own menu is used verbatim.

The newline after `<reserved_1>` is load-bearing, and the convention is v17's:

```
<reserved_1><reserved_3>   opens a call
<reserved_1>\n             opens prose
```

A no-call example written in the call shape would teach the model to read the format itself as the
instruction to call, and the contrast that teaches restraint would be lost.

Loss is masked to the assistant's own output only. For `toolcall_api` that is both the call **and**
the answer turn: reading a result back into the user's language is half of what a tool-calling
assistant does, and it is the half a demo is judged on.

One deliberate irregularity: a `toolpatch` exchange opens on an assistant call, because the pending
call it edits was never preceded by a generated user turn. Inventing one would teach a false
correspondence between a request and the arguments sitting next to it, which is worse than an
opening turn that a real client would have supplied anyway.

## The runs

One A100 each, because 209M and 503M parameters at bf16 leave an A100 64GB mostly empty and FSDP
would buy sharding nobody needs at the price of all-gathers on every layer. `--no-fsdp`.

Two settings had to be overridden.

**Batch.** The configs carry `global_batch_seqs: 256`, a *pretraining* batch: 1.05M tokens per step,
~50s/step on one GPU, which puts an 800-step fine-tune past 40 hours. Overridden to 32 seqs, 131k
tokens per step. Grafting a capability onto a converged checkpoint is better served by more steps at
a smaller batch.

**Schedule.** `--anneal 800` rather than a raw resume. The nano checkpoint is at step 10,000 of a
10,000-step schedule; resuming it plainly means `step >= total_steps` and the process exits having
trained nothing. `--anneal` starts the WSD decay at the resumed step and sets `total_steps` to
`step + 800`, so the LR lands at zero exactly when the fine-tune ends.

| | nano | mini |
|---|---|---|
| resume | `morena0p2b-nano/ckpt/step_00010000` | `morena0p5b-mini-sft/ckpt/step_00011500` |
| lr | 1e-4 | 7e-5 |
| micro batch | 8 | 4 |
| walltime | 6h | 8h |

### Launching

`train.py` calls `dist.init_process_group` unconditionally, **including under `--no-fsdp`**, so
`RANK`, `WORLD_SIZE` and `LOCAL_RANK` have to exist even for a single process. Exporting
`MASTER_ADDR` and `MASTER_PORT` by hand does not create them, and a plain `srun python train.py`
dies at rendezvous with `environment variable RANK expected, but not set`. `pretrain.sbatch` uses
`torchrun` for this reason; the only difference here is `--nproc_per_node 1`:

```
srun --kill-on-bad-exit=1 torchrun --standalone --nnodes 1 --nproc_per_node 1 train.py ...
```

A three-step throwaway run on the already-present sft17 shards (`tools_smoke.sbatch`) is what caught
this, at a cost of a few GPU-minutes instead of a six-hour job failing in its first seconds.

`mix_sft18_tools.json` replays **sft17 at 30%**. A tools-only run is the fastest way to get a model
that calls tools well and can no longer hold a conversation, and the general instruct and refusal
behaviour is what the release was actually judged on.

## Order

```
sbatch train/slurm/tools_sft_build.sbatch     # lrd_all_serial, CPU, one job per user
sbatch train/slurm/tools_sft_nano.sbatch      # boost_usr_prod, 1x A100
sbatch train/slurm/tools_sft_mini.sbatch      # boost_usr_prod, 1x A100
```

Then re-run `lab/sets/paystack_ng.json` against both. The number to beat is 9% raw, and the
Paystack menu is held out: it appears in no training record.
